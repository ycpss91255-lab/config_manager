# 回報、提問與開 issue 的細節

`AGENTS.md`「工作階段的規則」與「工作流程」的「開 issue 與發留言的條件」每條只寫一句（#411 的 Q9），細節放在這裡。

每一節開頭寫出處。「個人規則」指原本只存在維護者機器上 Claude Code 本機記憶裡的規則：別台機器、其他 agent 工具、cloud
工作階段都看不到，維護者定案（Q3 原話「放進 repo 不要放 global」）後寫進 repo。標「執行細節」（#411 審稿時補的做法，或協調工作階段
定的做法）與「協調工作階段的理解」的，都不是維護者原話。

## 回報給維護者的寫法

出處：個人規則（白話解說；回報的對象就是維護者本人）；協調工作階段的指示；Q3。

- 一律用繁體中文，包括工作中的進度句與指令的說明。
- 白話、一步一步教：用維護者看得懂的話解釋。要解釋的就解釋完整，只是寫得容易懂，不是為了簡短而省略。
- 第一行是結果或下一步：只讀第一行，就知道發生了什麼或要做什麼。
- 清單最多 5 項；超過就分成「現在做」與「之後」，或「必要」與「可選」。
- 多步驟的操作要編號，一步做一件事。

## 回報與提問之前

出處：個人規則（定期看全部 open issue、設計選擇分三類）；11/20 維護者意見（嫌問題太多）。

- 回報或提出待決問題之前，先讀相關 issue 的最新內文與留言：本文會被改，留言裡可能已有新的定案。
- 回報時把**提案**、**定案**、**實驗結果**分開寫，不混成一段。
- 已經定案的不重問。
- 提問前逐題對照全部定案：已定案的不問；例行選擇（下面「設計選擇分三類」第 1 類）自己決定，並寫出依據。

### 子工作階段的問題先送協調工作階段

出處：11/21 維護者原話「請問你沒有收到其他工作階段的問題嗎 為什麼是由工作階段直接問我」（經 config_manager 工作階段轉達）。
SendMessage、先做沒被擋住的工作、工具沒有 SendMessage 時的轉交方式，是執行細節。

1. 子工作階段先照上一節對照定案：能照既有定案或例行判斷決定的，直接決定並寫明依據，不問。
2. 真的需要人決定的，用 SendMessage 送給協調工作階段；不直接問維護者，也不把一輪結束在「等使用者回答」。
3. 協調工作階段先對照定案，能決定的自己決定；真的需要維護者決定的，才由它去問維護者。
4. 送出問題後，先做沒有被這個問題擋住的工作。真的無法繼續時，向協調工作階段交代卡在哪裡、需要它裁定什麼。
5. 有協調工作階段、但當下的工具沒有 SendMessage：把問題寫在這一輪最後回報的第一行，寫明要協調工作階段裁定什麼
   （Claude 桌面版的子工作階段，最後回報會轉給啟動它的工作階段）。
6. 沒有協調工作階段時，直接回報維護者，一樣先對照定案。

## 開 issue 前的審稿

出處：2026-11-24 維護者原話「不用 Codex。你再開一個窗口審核」（協調工作階段問「以後開 issue 前，要不要先給 Codex 審？」時，
在協調工作階段的對話裡回答）。下面標「協調工作階段的理解」「執行細節」的，不是維護者原話。hook 見 #413。

- **審什麼**：issue 草稿（標題與內文全文），以及已開 issue 的本文修改（改本文也要審：協調工作階段的理解）。
- **誰審**：協調工作階段另開的審稿工作階段（「另開窗口」理解成另開審稿工作階段：協調工作階段的理解）。不經 Codex；寫的人不自己審，
  協調工作階段自己寫的草稿也一樣交給另開的審稿工作階段。
- **怎麼送**（執行細節，協調工作階段定的）：子工作階段寫好草稿後，用 SendMessage 請協調工作階段開審稿工作階段，不自己開；沒有協調
  工作階段時，寫草稿的工作階段請維護者另開。草稿存成檔，送審時給檔案位置；草稿引用的遠端事實（issue、PR、commit、檔案位置）附出處，
  讓審稿工作階段自己核對。
- **怎麼處理意見**：逐點處理，採納就改，不採納附證據；改完再送審，直到判「可以開」。
- **開了或改了之後**：在 issue 留言附最後一輪的判定，與適合公開的意見摘要；不貼本機路徑。協調工作階段向維護者簡單說明審了哪些項目
  （2026-11-21 #407 定案 15 的說明要求，11/24 沒有改）。
- **不必問維護者**：判「可以開」就開（11/20 Q6 前半「開 issue 不用問我」）。需要 owner 層級或架構決定的事，仍照 `AGENTS.md`「工作流程」
  的「自己無法決定的事」等維護者決定，審稿不取代那個決定。
- **不亂開、不開了又關**（個人規則）。

### 要發的留言與一般進度

- **要發的留言**（回寫到其他 issue 的內容、對外的更正，例如 #407 回寫 #373 那則）：由協調工作階段自審（2026-11-21 #407 定案 15，現行），
  向維護者簡單說明審了哪些項目，然後就發；不送審稿工作階段。11/24 的問句只問開 issue，所以這一半不變：協調工作階段的理解。
- **工作階段在自己的 PR、issue 上寫進度和結果**：不必先給協調工作階段審（協調工作階段的指示，11/24）；照下面「精確措辭」寫，也照
  `AGENTS.md`「Commit 訊息」不加署名、不放本機路徑。

## 精確措辭

出處：個人規則（精確措辭）。

1. 事實與推論分開；推論要標明是推論。
2. 歸因要有佐證：例如量到的是「計時落差」，不能寫成「睡眠」。
3. 用精確名稱：例如「有相符的快取」不等於「命中」，「故障注入」不等於「突變檢查」。
4. 不默默放寬保護：要放寬就寫明，並附依據。
5. 說明互相矛盾時，先改正。
6. 更正證據要留修改紀錄：寫明改了什麼、為什麼改，不直接蓋掉舊的。

## 設計選擇分三類

出處：個人規則（設計選擇分三類）。

1. **例行實作選擇**（旗標名稱、輸出格式、一般做法）：自己決定、寫依據，不列成待批。
2. **測試介面流程**：看是不是新的觀察位置（`doc/TEST-PLAN.md` 對測試介面的定義），不是看有沒有新增腳本。是新的觀察位置，才走
   `AGENTS.md`「TDD」的「新增一個測試介面」四步。
3. **驗收規則變更**（什麼算通過、什麼證據可以接受）：要有依據或維護者確認。

## issue 提案底線

出處：個人規則（issue 提案）。

1. 不預設縮小驗收範圍。
2. 不把某一項驗收當成其他項的共同前置，除非有依據。
3. 事實與推論分開。
4. 草稿全文貼出、審過才發（審稿照上面「開 issue 前的審稿」）。
5. 核可發留言不等於核可實作。
