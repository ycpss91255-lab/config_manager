# 新納管的預設主機名稱由開發者確認、存在清單檔；候選由啟動工具在主機上取得

> 服務：不變式 8（身分只來自明確、檔案記錄的設定）、不變式 2（絕不靜默失敗）、不變式 4（預設值落向安全）

- **Date:** 2026-11-17
- **Status:** Accepted
- **Relates to:** ADR-00000012（身分三欄位）、ADR-00000031（compose 疊加檔）、ADR-00000020（身分是自我宣告）；#178、#353、#385

## Context

設計文件 §4.3 寫「納管當下讀取本機 hostname 作為預設值填入，之後永不再讀」；PRD 不變式 8 寫
命名的分歧「來自明確的、檔案記錄的 override，絕不來自環境變數」。#178 為了 bridge 網路下容器
讀到的名稱是每次重建都換的容器 ID，改由 `CM_HOSTNAME` 環境變數決定納管時的名稱——它解決了
穩定性，卻是環境變數來源，而且沒有明確取代不變式 8。#353 對照 v0.2.0 檢查點 1 時發現這個矛盾，
維護者 11/17 決定改由明確保存的設定為唯一來源。

原文**沒有指定**這個預設值存在哪、怎麼取得、誰能改、取得失敗時怎麼辦。以下是在原文未指定之下
的設計決定，依據是維護者 11/17 的幾輪定案（#385 的內文與留言），不是原文的規定。

## Decision

1. **存放**：這台機器的納管預設名稱存在 `config-list.toml` 的 `[defaults] hostname`——用途是
   「納管時的預設值」，`[defaults]` 的語意正是「未個別指定時套用」；不新增檔案或掛載。只在納管新
   config 時預填，確認納管後寫進那一筆；既有條目一律讀自己的 hostname，修改預設值不替它們改名；
   舊條目缺 hostname 是資料問題，不以預設補上。還沒保存時只擋需要名稱的納管（後端也擋）。
2. **候選**：啟動工具（`just docker run`／`bridge run`／`dev run`）的 post-run hook 在**主機**上讀
   `hostname`，經 `docker compose exec` 以標準輸入交給容器裡的寫檔程式記下；服務只讀，開發者
   確認後才保存。候選**只認本次服務啟動**：服務每次啟動產生隨機的啟動識別碼、留在記憶體，不看
   檔案時間。**同一次啟動已有有效候選時不更新**，畫面稱它「本次啟動取得的候選」、不保證是即時的
   主機名稱。寫入工作綁定開始時取得的識別碼，中途不換。
3. **候選放在容器可寫層的 `/run/config_manager/`**：不在設定庫、不在任何資料卷，服務使用者擁有
   （目錄 0700、檔案 0600），entrypoint 每次容器啟動時清空。候選只對一次啟動有效，保存下來沒有
   用處；現有的 `git bundle` 備份、資料卷打包、設定庫複製都不包含它。
4. **權限與紀錄**：查看不需要編輯權；確認與修改限開發者角色、需要編輯權，後端檢查；每次確認與
   修改以一筆 commit 記下修改前後的值與操作者。開發者角色是自我宣告（ADR-00000020），不當成
   安全保證。
5. **啟動工具的結束碼**：候選取得失敗只警告、以 0 結束——服務已經起來，不擋啟動；寫檔程式失敗時
   再查 backend 的狀態，不在執行中或查不到狀態就以非零結束，不把服務啟動失敗吞掉。啟動工具不檢查
   就緒，所以不說服務正常。畫面只顯示服務實際知道的原因。
6. **殘留 `CM_HOSTNAME`**：主機端（pre-run hook：環境變數與 repo 根目錄的 `.env`，逐行當文字讀、
   不執行，空值也算）與容器端（entrypoint）都停止啟動，訊息寫明順序「先移除舊變數 → 啟動服務 →
   到介面確認名稱」。
7. **CLI**：照 #355 的定案排在 v0.10.0；這次只做介面與後端。

## Alternatives

- **`CM_HOSTNAME`（#178）／候選專用的環境變數**：仍是環境變數來源，與不變式 8 相衝突。
- **服務起來後由啟動工具呼叫 API**：多一個端點，還要處理服務還沒就緒。
- **比對候選檔的修改時間**：複製、還原會改變時間；主機與容器的時鐘可能不同；`compose up` 可能
  沿用既有容器（維護者 11/17）。
- **每次執行啟動工具都重建服務（`--force-recreate`）**：讓「寫入失敗時舊候選一定屬於別次啟動」
  成立，但為了更新一個候選名稱，重跑啟動工具必定中斷服務、重置編輯階段，影響太大（維護者
  11/17 否決）。代價是同一次啟動裡重跑時取得失敗，先前取得的有效候選仍然有效。
- **掛主機的 `/etc/hostname`、比對容器 ID 的形狀**：#178 已否決（掛載前提；形狀判斷脆弱）。
- **依網路模式決定要不要信容器讀到的名稱**：只對有證據的部署配置成立。
- **候選放在設定庫根目錄並列進 `.git/info/exclude`**：exclude 只影響 Git 的追蹤判定，打包資料卷
  仍會帶走它；候選只對一次啟動有效，不必保存。

## Consequences

- 清單檔多一個 `[defaults] hostname`；`load` 對不安全的值與條目缺 hostname 都具名失敗。
- 新端點 `GET`／`PUT /api/host-name`；頁面多全域「設定」（W10）；納管確認頁在沒保存名稱時顯示
  缺少與設定入口、不能完成。
- `io/source.local_hostname()` 移除；compose 不再把 `CM_HOSTNAME` 帶進容器，bridge 疊加檔不再
  要求它。升級順序：先移除舊變數 → 啟動服務 → 到介面確認名稱。驗證環境以 `docker run -e
  CM_HOSTNAME=…` 起服務的腳本，換版時要先拿掉它，否則會被 entrypoint 擋下。
- 直接用 `docker compose up`（不經啟動工具）時沒有候選，畫面顯示目前主機名稱尚未確認；主機端的
  殘留檢查也做不到——名稱不受影響，因為服務已不讀它。
- 同一次服務啟動裡主機改了名，候選不會跟著更新；服務真正重啟時舊候選才失效。
